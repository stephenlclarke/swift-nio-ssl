# fix: send bad certificate alert for Darwin trust failures

## Motivation

Darwin's default trust verifier needs to select `bad_certificate` when a client rejects a server certificate. Server-side client-certificate rejection and public custom verification callbacks continue to leave alert selection to BoringSSL. [PR #605](https://github.com/apple/swift-nio-ssl/pull/605) also has an upstream review request to keep BoringSSL's alert pointer at the C callback boundary.

## Implementation

Rebase the existing alert fix onto upstream `86458a336bf0f647b080c8637515bfefd8ea08b3`, retaining its updated BoringSSL and shim functions. `CustomVerifyManager.process` returns `(ssl_verify_result_t, UInt8?)`, with a configured alert only on a client connection; the `SSL_set_custom_verify` callback writes that optional alert to `outAlert`. Focused tests cover client and server failure, public failure, success, pending verification, and Darwin default configuration.

## Validation

With four build jobs and a dedicated scratch path, `swift test --filter CustomVerifyManagerTests` passed 7/7 and `swift test --filter NIOSSLTests` passed 348/348. The failed first full run and the initial C shim compile failure remain in the retained audit logs. All three existing server-side alert assertions passed unchanged after the role-scoped correction.

## Compatibility and remaining risk

No public Swift API changes. Upstream's new BoringSSL is retained. Hosted PR checks still need to run before merge. This local preparation has not been pushed or commented on GitHub.
